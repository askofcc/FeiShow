# 项目灵魂：为什么做 FeishuNext

> 本文回答三件事：**痛点是什么、我们补齐什么、现在做到哪、以后往哪走。**  
> 这是整个项目的动机层；契约与实现细节见其它 `docs/feishu/*`。  
> 讨论过程、阶段结论与运维注意见 [DECISION_LOG.md](./DECISION_LOG.md)。  
> 日期：2026-07-25

---

## 1. 一句话

> **官方飞书文档 API 是为「在线编辑 / 协作 / 权限」设计的；我们是为「对外展示」把同一份数据洗成可读、可渲染、可再分发的结构。**

灵魂不在「再做一个博客主题」，而在：

**把飞书 API 返回的复杂 JSON，转化为展示场景真正能用的结构化数据。**

---

## 2. 核心痛点

### 2.1 飞书文档是什么

飞书云文档 / 知识库节点是**富文本、灵活型**文档：

- 编辑器能力强：块、表格、分栏、嵌入、附件、权限、评论……  
- API 返回的是**编辑态友好**的块树与元数据，不是「一篇文章的干净正文」

### 2.2 为什么「API JSON 不可直接阅读」

| 维度 | 官方设计目标 | 展示场景需要 |
|---|---|---|
| 结构 | 编辑、协同、权限、版本 | 标题 / 段落 / 列表 / 图 / 目录 |
| 粒度 | block、parent、children、style 嵌套 | 线性可读 + 稳定中间模型 |
| 权限 | 谁能改、谁能看、谁能分享 | 能不能渲染；不能则提示 |
| 消费方 | 飞书客户端 / 管理后台 | 独立站、SEO、RSS、后续 Agent |

因此：即使一篇普通文档，官方 JSON 也充满格式标记与嵌套。  
**直接当 CMS 正文用，易读性极差，前端也不好接。**

这不是「API 坏了」，而是：

> **官方场景 = 在线文档编辑与管理；我们的场景 = 信息展示。**  
> 场景不同，数据形态就不该原样复用。

---

## 3. 核心价值（我们补齐什么）

### 3.1 相对官方，优势从哪来

官方已经覆盖「写」和「管」；缺的是**面向外部世界的展示层**：

| 官方强 | 官方弱 / 非目标 | 我们做 |
|---|---|---|
| 编辑体验、协作、权限 | 独立站阅读体验 | 站点壳（NotionNext 二开） |
| 企业内部可见性 | SEO / 自定义域名 / 主题 | 公开 Web 资产 |
| 原始 blocks JSON | 易读结构、稳定渲染契约 | normalize → `FeishuBlock` / `Post` |
| 权限体系本身 | 对外展示失败时的产品体验 | accessError / PostLock 等 |

**展示场景比编辑场景简单得多**：只读、可缓存、可 ISR、不需要完整编辑语义。  
所以我们可以做得更轻、更稳、更适合公开分发——这是相对「直接打开飞书公开页」的优势，不是跟飞书抢编辑器。

### 3.2 价值公式

```text
飞书 OpenAPI（权威数据源）
    → 清洗 / 归一 / 重组（本项目灵魂）
    → 结构化中间模型（可读、可测、可渲染）
    → 站点展示 / SEO / RSS /（未来）AI 消费
```

第一性原理：

1. **数据在飞书**（不迁移写作习惯）  
2. **消费在展示**（独立站，不是再做一个编辑器）  
3. **中间必须结构化**（否则前端与 AI 都接不动）

## 4. 当前进展（分两层）

### 4.1 第一点（已完成）——数据结构化

**定义：** 解决「飞书文档 JSON 难以直接使用」的问题。

| 层 | 含义 | 仓库落点（主工程） |
|---|---|---|
| 取数 | 官方 OpenAPI 稳定路径 | `lib/feishu/*`、`STABLE_FEISHU_DATA.md` |
| 归一 | blocks → `FeishuBlock` / `FeishuPageContent` | `normalize.ts`、`FEISHU_BLOCK_MAPPING.md` |
| 站点索引 | 内容表 + CONFIG + 分类展开 | `adapters/feishu/*`、内容/配置契约 |
| 渲染 | 展示用结构 → 页面 | `FeishuRenderer` / `FeishuPage` |
| 契约 | 字段与权限边界写死 | `FEISHU_DOCUMENT_CONTRACT.md` 等 |

**验收标准（产品语言）：**

- 人能在独立站上读懂一篇飞书文章  
- 机器能拿到稳定的 `Post` / blocks 中间模型，而不是原始飞书 JSON 大杂烩  
- 权限失败可预期，不静默崩站  

> 现阶段所有工程决策，优先服务「结构化是否正确、是否可维护」，而不是堆主题皮肤。

### 4.2 第二点——AI 就绪度（数据出口，第一刀已落地）

在同一份结构化数据上，给机器只读出口。不是问答机器人，也不是再打一遍飞书。

| 已有 | 说明 |
|---|---|
| `/llms.txt` | 发现 |
| `/api/agent/posts` | 列表 JSON（同一份站点索引） |
| `/api/agent/posts/:slug` | 单篇 JSON + Markdown（同一份 `feishuContent`） |

调用说明：[AGENT_API.md](../feishu/AGENT_API.md)

**后置：** 向量库、RAG、站内问答、写回飞书。

## 5. 和 NotionNext / 飞书官方的关系（边界）

| 对象 | 我们学什么 | 我们不学什么 |
|---|---|---|
| NotionNext | 站点壳、主题、SEO、列表/阅读信息架构 | Notion recordMap 宗教、伪造 Notion 数据 |
| 飞书官方 | 权威内容与权限真相 | 编辑器、完整权限后台、protobuf 网页接口当基座 |

**不做：** 再造飞书文档编辑器。  
**要做：** 展示向的「飞书 → 结构化数据 → Web + 机器出口」。

---

## 6. 对后续开发的约束（写进灵魂，避免跑偏）

1. **任何新功能先问：** 是展示路径需要，还是在模仿编辑/管理？后者默认不做。  
2. **中间模型优先于主题：** 主题可换；`Post` / `FeishuBlock` 契约要稳。  
3. **官方 API 主路径：** 不稳定网页接口不进灵魂路径。  
4. **AI 只做数据出口：** 列表/单篇 JSON+MD 可以；向量库/问答不当主里程碑。  
5. **复杂度只加在「清洗与适配」：** 壳尽量二开复用，不从头手搓 UI 宇宙。

## 8. 一句话收束

> **痛点：** 飞书 JSON 为编辑与权限而生，展示不可直接用。  
> **价值：** 清洗重组为展示向结构化数据，并挂上独立站能力。  
> **现在：** 结构化数据 + 人读站 + 机器 JSON/Markdown 出口。  
> **下一步：** 部署收敛（用户只填少量参数）；AI 侧先稳这个出口，不另起炉灶。
