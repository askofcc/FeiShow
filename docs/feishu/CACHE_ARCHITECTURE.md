# 飞书 CMS 缓存架构与分级治理指南

在将飞书（Feishu）作为无头内容管理系统（Headless CMS）时，由于飞书开放平台存在调用频率限制（QPS 限流 `99991400`），且富文本云文档体积较大，**科学的分层缓存、梯级并发控制与防打爆机制**是保障站点高性能与高可用的核心生命线。

本文档详细记录 FeiShow 的缓存体系设计、梯级并发调度、防故障熔断机制以及配置中心字段说明。

---

## 一、 核心设计思想

> **“API 数据层必须做分级缓存与跨页面去重，高频配置和低频正文必须在生命周期（TTL）上彻底解耦；并发调度必须在冷启动时削峰防抖，彻底消除飞书 API 频控封禁。”**

系统将数据划分为三种完全不同生命周期的类型，实施差异化治理：

```text
┌─────────────────────────────────────────────────────────────────────────────────┐
│ 1. 高频元数据层（配置表 CONFIG / 内容表 Content / 菜单 / 分类列表）            │
│    - 特点：站长调样式、改菜单、建分类时可能频繁变动，但数据量极小（纯轻量表格）      │
│    - 默认 TTL：5 分钟（300 秒，调试期可通过配置设为 5 秒）                      │
│    - 控制字段：CONFIG_REVALIDATE_SECOND / NEXT_REVALIDATE_SECOND                │
└─────────────────────────────────────────────────────────────────────────────────┘
                                         │
┌─────────────────────────────────────────────────────────────────────────────────┐
│ 2. 低频正文内容层（文章正文 Blocks / 文档元属性 / 目录树 TOC）                  │
│    - 特点：作者写完文章发布后极少频繁改动，数据量较大（树状 Blocks）            │
│    - 默认 TTL：24 小时（86400 秒，支持自由自定义）                              │
│    - 控制字段：POST_REVALIDATE_SECOND                                           │
│    - 机制：【一次请求，全局复用】某篇文档抓过一次正文后，内存长效锁定，          │
│            无论列表、正文页、RSS、搜索怎么调用，100% 命中缓存，0 重复请求       │
└─────────────────────────────────────────────────────────────────────────────────┘
                                         │
┌─────────────────────────────────────────────────────────────────────────────────┐
│ 3. 超低频资产层（图片 Media Proxy / 封面图 / 画板 / 附件素材）                  │
│    - 特点：二进制大文件（单张 1MB~8MB），消耗带宽和飞书下载配额                 │
│    - 默认 TTL：30 天浏览器缓存 + 1 年 (31536000秒) Edge CDN + immutable 永久免回源 │
│    - 机制：Token 唯一且不可变，CDN 边缘节点常驻，全球秒开，彻底隔绝飞书 API 穿透│
└─────────────────────────────────────────────────────────────────────────────────┘
```

## 二、 梯级并发控制与流量削峰调度（API Concurrency & Rate Limiting）

飞书开放平台针对单应用的 API 请求通常有 **20~50 QPS** 的频控限制与瞬间突发脉冲阈值。当整站有数十篇文章同时更新或首次构建时，必须通过**精细化并发控制**阻断 429 报错：

### 1. 梯级并发控制矩阵

| 任务类型 | 并发数 | 调用的飞书接口 | 优化与防护原理 |
| :--- | :--- | :--- | :--- |
| **文档属性批量查询** | **1 个请求（无并发）** | `POST /drive/v1/metas/batch_query` | **批量接口合并**：单次 HTTP 请求直接打包查询 50 篇文档属性，绝不使用循环单篇请求。 |
| **Wiki 节点解析** | **最大 6 并发** | `GET /wiki/v2/spaces/get_node` | 轻量 ID 换取接口，并发设为 6 可在 200ms 内极速解析全站节点，且远离频控线。 |
| **正文摘要补齐** | **严格 2 并发** | `GET /docx/v1/documents/:id/blocks` | 正文 Blocks 属于重型接口。合并为全局单一队列，最大仅允许 2 个并发任务同时运行。 |
| **文档封面补齐** | **严格 2 并发** | `GET /docx/v1/documents/:id` | 读取文档元数据中的封面 token，同样以 2 并发平稳采集。 |
| **表格预填跳过机制** | **0 请求（直接跳过）** | 无 | 若多维表格中已手动填写了「摘要」或「封面」列，系统直接使用表格数据，**零网络请求**。 |

### 2. 防并发击穿（In-flight Anti-Stampede）
- 在全站数据刷新（`fetchSiteFromFeishu`）期间，即使有 100 个访客在同一毫秒内同时刷新过期的页面，系统会通过 Promise 共享机制（`siteDataInflight`）**只向飞书发出 1 次真实全站拉取请求**，其余 99 个访客在内存中挂起等待，拿到同一份结果后同时返回，杜绝缓存击穿。

### 3. 指数退避重试（Exponential Backoff Retry）
- 底层 `feishuFetch` 客户端内置频控拦截器：若飞书网关偶尔返回 `99991400`（频控超限）或 HTTP 429/502，客户端自动执行指数级休眠（`800ms`、`3200ms`...）并自动重试最多 3 次，对上层业务 100% 透明无感。

## 三、 配置中心（CONFIG 表）字段说明

在飞书多维表格「配置中心（CONFIG 表）」中，可以通过以下字段灵活控制各层级缓存：

| 配置名 | 适用范围 | 默认值 | 推荐配置场景 |
| :--- | :--- | :--- | :--- |
| **`CONFIG_REVALIDATE_SECOND`**<br>*(兼容 `NEXT_REVALIDATE_SECOND`)* | **配置中心、分类列表、导航菜单、主题切换** | `300`（5分钟） | **调试期**：填 `5` 开启 5 秒极速同步；<br>**生产期**：填 `300` 保护 API。 |
| **`POST_REVALIDATE_SECOND`** | **文章正文内容、文档 Blocks、独立页面 ISR** | `86400`（24小时） | 低频内容，默认 24 小时，彻底杜绝大体积 Blocks 递归请求打爆飞书 API。 |

## 四、 四重防故障与自愈机制（Anti-Poisoning & Fault Tolerance）

为避免因偶发网络抖动导致网站故障，系统内置了 4 重企业级防故障熔断策略：

### 1. 拦截负向缓存投毒（`isCacheableValue` 守卫）
- **问题**：如果某次请求飞书偶然超时或返回空，若将空结果存入缓存 24 小时，会导致网站长时间错误。
- **对策**：在底层 `lib/feishu/memo.ts` 中，所有返回 `null`、`undefined`、空数组或临时网络错误（502/504）的结果，**严禁存入长效缓存**，并立即在内存中删除该 Key，保证下一次请求能立刻发起自愈重试。

### 2. 故障陈旧数据兜底（`Stale-If-Error`）
- **问题**：飞书 API 瞬时不可用时，系统如果抛出空页面或报错，会破坏访问体验。
- **对策**：在 `lib/cache/cache_manager.js` 中，一旦向飞书拉取失败，系统**坚决不覆盖历史缓存**，而是自动提取并返回上一份**健康的完整历史全站缓存**（包括全部文章、分类、菜单），保证读者端永远 100% 正常可读。

### 3. 媒体代理防错误缓存
- **问题**：飞书图片代理若遇频控返回 JSON 错误体，若被 CDN 缓存会导致图片长时间裂开。
- **对策**：在 `/api/feishu/media/[token].js` 中，一旦发现非图片或空字节响应，强制输出 `no-store, no-cache, max-age=0`，CDN 绝不缓存错误。

### 4. 跨页面内存共享池（Deduplication）
- 同一篇文档的 Blocks 和元数据在当前进程的生命周期内**只向飞书请求一次**；
- 生成正文、目录 TOC、摘要和预览时，100% 共享同一份内存数据，绝不发起任何重复的飞书网络调用。

## 五、 常见问题与排障

### 1. 为什么在飞书里改了菜单，网页刷新没有立即变？
- **原因**：全站菜单受 `CONFIG_REVALIDATE_SECOND` 保护（默认 5 分钟）。
- **解决**：在飞书 CONFIG 表将 `CONFIG_REVALIDATE_SECOND`（或 `NEXT_REVALIDATE_SECOND`）设为 `5` 并启用，即可实现 5 秒内刷新生效。调试完毕后改回 300。

### 2. 怎么立即强制全站更新？
- 在 Vercel 部署控制台点击右上角 **「Redeploy」**，Vercel 会在 30 秒内清空所有 CDN 缓存并拉取飞书最新数据重建。

### 3. 图片在冷启动加载时为什么比文字慢？
- 飞书原图未压缩（单张常有数 MB），冷启动时需由 Vercel 从飞书下载后回传；
- 系统已对媒体设置了 **30 天浏览器 + 1 年 CDN 永久不可变缓存**，首位访客加载后，后续所有人访问均由全球 CDN 边缘节点秒级响应。
